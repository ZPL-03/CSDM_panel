# 案例迁移机制详解

## 1. 候选生成中的位置

`CASE_TRANSFER` 是候选生成的三条来源之一：

| 来源 | 主要输入 | 输出方式 |
|---|---|---|
| `LLM` | 任务约束、用户明确事实、外部知识库/知识图谱片段 | LLM 工程自然语言候选表，再由系统解析 |
| `CASE_TRANSFER` | 历史案例档案、正式案例库、案例记忆索引 | 迁移可复用案例的设计参数 |
| `DOE` | 参数空间与任务约束 | 采样生成并补足候选池 |

当前初始来源比例为 `LLM:CASE_TRANSFER:DOE = 2:1:1`。配额只决定优先尝试数量；案例迁移没有足够可用样本时，DOE 负责补足候选池。

## 2. 数据边界

案例迁移读取三类案例侧资产：

- `data/cases/`：所有校核档案，当前 350 个。
- `knowledge/case_library/`：满足正式入库条件的案例，当前 41 个。
- `knowledge/chroma_db/` 的 `csdm_case_memory`：案例记忆索引，当前 350 条。

外部知识库/知识图谱属于 LLM 候选路径，不承担案例迁移。案例迁移也不把历史案例原文拼入 LLM Prompt。

## 3. 检索和过滤

入口在 `core/case_retriever.py`。`retrieve_transferable_cases()` 先扫描案例记录，再按硬条件和排序规则返回可迁移案例。

可迁移案例必须满足：

1. `abaqus_results.status == "success"`。
2. 案例结论为通过。
3. `design` 存在且可形成候选。
4. 与当前任务达到迁移匹配级别。

迁移匹配要求当前任务和案例设计至少满足：

- 筋型一致。
- 工况类型一致。
- 边界类型一致。
- 材料名称未形成冲突。

`CaseMemoryIndex` 提供向量排序辅助。向量召回不能替代上述硬条件；案例能否迁移仍由结构化字段决定。

## 4. 排序

结构化候选使用工程距离排序，分数越低越靠前。当前评分关注：

- 等效面内载荷差异。
- 板长、板宽、筋高差异。
- 当前目标 BLF 与历史校核 BLF 的差异。
- 案例记忆向量排名的轻量修正。

实现中载荷项权重为 `1.0`，板长和板宽项为 `0.02`，筋高项为 `0.05`，BLF 差异项为 `100.0`，向量排名修正项为 `0.1`。这使排序首先服从当前任务工况和稳定性余度，再用案例记忆相似性处理同类案例之间的先后顺序。

## 5. 迁移成候选

`agents/candidate_gen.py` 将案例设计规范化成当前任务候选：

- 几何、铺层、材料来自历史案例设计。
- 候选来源写为 `CASE_TRANSFER`。
- 载荷、边界和设计目标改用当前任务约束。
- 候选身份使用会话内 `TMP_<n>`。
- `rationale` 和来源说明保留历史案例线索。
- 进入下游前必须通过 `RuleChecker`。

因此案例迁移不是把旧案例当作新校核结果，而是把已经验证过的设计作为当前任务候选，再进入初筛和真实 Abaqus 校核。

## 6. 配置

来源比例配置位于 `config/app_config.yaml`：

```yaml
pipeline:
  candidate_source_ratio:
    llm: 2
    case_transfer: 1
    doe: 1
```

案例记忆混合检索配置也在同一文件中：

```yaml
case_memory:
  hybrid_retrieval: true
  vector_top_k_multiplier: 4
  vector_rank_weight: 0.1
```

## 7. 回流关系

真实 Abaqus 校核后的样本由 `KNOWLEDGE_AGENT` 回流：

- 全部校核样本写入 `data/cases/`。
- 满足正式入库条件的案例写入 `knowledge/case_library/`。
- 案例摘要和元数据写入 `csdm_case_memory`。

下一个任务的案例迁移只读取这些案例侧资产。失败档案可用于追溯和代理模型样本管理，但不作为可迁移通过案例。
